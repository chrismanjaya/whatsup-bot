# WhatsUp — WhatsApp Finance Tracker Bot

## Architecture
Clean Architecture, as onion layers (each layer imports only layers closer to the center):
1. internal/domain — entities + rules that don't depend on a process (Transaction, Category, TransactionType...). Imports nothing.
2. internal/repository, internal/parser — interfaces the usecases need from outside (storage, text parsing) plus their data types. Import only domain.
3. internal/usecase — business processes, one subpackage per feature: transaction (record, amend, query, page, summarize), user (register), group (ensure, membership, split). Supporting packages at the same level: usecase/response (Reply, a leaf package so every usecase can share it without import cycles), usecase/message (all reply text), usecase/persona (Frankie's variant picker).
4. internal/external — implementations of the outside world: whatsapp (inbound: receives events, sends replies), gemini (implements parser.MessageParser), database (SQLite, implements the repository interfaces).
5. cmd/bot — composition root, the only place importing concrete external packages.
Side packages any layer may import: internal/constant (sentinel errors, fixed values) and internal/util (logging, error wrapping); they never import a layer package. internal/config is read only by cmd/bot.

cmd/bot: main.go (load config, connect, wait for signal, disconnect) and wire.go (build() constructs the external packages + usecases and registers the WhatsApp handler). Env is read only in internal/config. WhatsApp-specific work lives in internal/external/whatsapp: client.go (store/client setup, QR pairing + connect), handler.go (event parsing, group/membership ensure, typing presence, sending replies, storing wa_message_id) and queue.go (per-chat worker). Routing lives in the usecase layer: internal/usecase/dispatcher.go (Dispatcher.Handle picks the usecase for a usecase.Incoming message, in priority order: self-echo guard, quoted-reply context, register/split commands, summary/query, else record; plus replyForError). It has no whatsmeow dependency and is tested with fake repositories in dispatcher_test.go.

## Conventions
- Enums as typed strings with String()/Valid()/ParseX() constructors (see domain/transaction.go's TransactionType, domain/category.go's Category).
- domain.Category.AllCategories is the single source of truth for valid categories — Valid(), the Gemini schema Enum, and the prompt's category list all derive from it. Add/remove categories there only.
- Errors: usecases return sentinel errors from internal/constant, classified into user-facing messages by replyForError() in internal/usecase/dispatcher.go via errors.Is(), with the wording taken from internal/usecase/message. Don't return raw message strings from usecases for expected failure paths.
- User-facing text: every reply string/template (errors, welcome, split, confirmations) lives in internal/usecase/message — message.go for fixed templates, pools.go for Frankie's randomized variants (error replies and quip fallbacks). Edit wording there, don't inline strings in usecases or the dispatcher. BotReplyPrefixes in that file drives the dispatcher's self-echo guard, so a new reply template's first line must be added there.
- Config: read via internal/config.Load() (add new env vars there, with defaults). Single source of truth is GitHub Secrets, written to ~/whatsup-bot.env on the VM by the deploy workflow, loaded via systemd's EnvironmentFile=. Never hardcode secrets or set env vars manually on the VM.

## Known gotchas / decisions made
- Gemini model: internal/config's default (when GEMINI_MODEL is unset) is gemini-3.6-flash — a deliberate choice, keep it. Override via the GEMINI_MODEL secret. If quota becomes a problem, use gemini-3.5-flash-lite (or check https://aistudio.google.com/rate-limit for current best Lite-tier model). Non-lite Flash models have a ~20 requests/day free-tier cap — too low for real use. Lite tier gets ~500/day.
- Retry logic distinguishes 503/UNAVAILABLE (retry with backoff) from 429/RESOURCE_EXHAUSTED (quota — fail fast, retrying can't help).
- ThinkingConfig.ThinkingBudget=0 disables reasoning tokens — needed to stop token usage ballooning on non-lite models (lite models don't seem to need this).
- transaction_date (user-stated, can be backdated via "kemarin" etc.) is separate from created_at (audit timestamp, always now()) — don't conflate them.
- Self-echo guard: the whatsapp Handler's handleEvent (handler.go) checks v.Info.IsFromMe first (the real fix) and Dispatcher.Handle (internal/usecase/dispatcher.go) also still checks reply-text prefixes (e.g. "*EXPENSE*", "*DELETED*") as a belt-and-suspenders check — if IsFromMe ever proves unreliable on some WhatsApp client, the prefix list is the fallback. Update message.BotReplyPrefixes (internal/usecase/message/message.go) if a new outgoing reply template's first line changes.
- No migration tooling — still in sandbox phase, so schema changes just edit initSchemaQuery (CREATE TABLE IF NOT EXISTS) in internal/external/database/const.go and assume a fresh DB (delete whatsup.db and let it recreate). Revisit once there's real data worth preserving across schema changes.
- Only the transaction's original recorder can update/delete it via reply (checked by user.ID == tx.UserID in transaction.AmendUseCase) — even for shared/group transactions, other group members can't amend someone else's entry. Revisit if that turns out to be too restrictive for shared expenses.

## Deploy
Push to main -> GitHub Actions builds binary on the runner (not the VM, too slow) -> scp's it -> SSH restarts systemd service via a scoped passwordless sudo rule (systemctl restart whatsup-bot only).

## Update/delete via reply (done)
Reply to a bot transaction confirmation to edit or delete it — no visible transaction ID is shown to the user; matching happens purely through WhatsApp's own quoted-reply mechanism.
- Outgoing confirmations are captured via client.SendMessage's resp.ID and stored on the transaction row (transactions.wa_message_id) through TransactionRepository.SetWAMessageID, called from the whatsapp Handler right after a successful send.
- Incoming replies are detected via v.Message.GetExtendedTextMessage().GetContextInfo().GetStanzaID() in the whatsapp Handler's handleEvent and passed into Dispatcher.Handle as Incoming.StanzaID; when non-empty, it's tried against transaction.AmendUseCase before falling through to the normal register/split/record flow.
- transaction.AmendUseCase (internal/usecase/transaction/amend.go) looks up the transaction by wa_message_id, checks ownership, then calls MessageParser.ParseAmend (Gemini) with the transaction's current fields to decide action: "update" | "delete" | "none". On update it re-renders the same *EXPENSE*/*INCOME* confirmation template (so a reply to that follow-up also resolves correctly once its own wa_message_id is set), on delete it sends a *DELETED* confirmation, and "none" asks the user to clarify.
- If stanzaID doesn't match any stored wa_message_id (e.g. reply to an unrelated bot message), transaction.AmendUseCase reports handled=false and the dispatcher falls back to normal handling instead of erroring.

## Query transactions with paging (done)
"transaksi tanggal 1 agustus", "transaksi kemarin", "transaksi bulan agustus" list the sender's own transactions (by transaction_date, oldest first), one WhatsApp message per transaction in the normal *EXPENSE*/*INCOME* format, so each can be replied to for update/delete.
- transaction.QueryUseCase pre-filters on keywords (queryKeywords) before calling MessageParser.ParseQuery (Gemini), so ordinary transaction messages don't cost an extra model call. It runs after register/split and before transaction.RecordUseCase; handled=false falls through to recording.
- 10 transactions per page (queryPageSize). When there are more pages, a *PAGE n/N* summary message follows; its wa_message_id is stored in query_pages (with the date range and page). Replying to it ("next"/"lanjut", "prev"/"sebelumnya", "page 3") is resolved by transaction.PageUseCase, tried in the dispatcher right after transaction.AmendUseCase. Command parsing is plain Go (parsePageCommand), no Gemini call.
- Usecases return []response.Reply (Text + optional Tx/Page to link the sent message ID to); the whatsapp handler sends them in order with a short sendInterval pause. Date filtering compares substr(transaction_date,1,10) as text because stored timestamps carry a UTC offset.

## Summary report (done)
"summarize this month", "this week report", "laporan bulan agustus" reply with one *SUMMARY* message: expense/income totals and counts, top category (largest total amount, not most frequent) and biggest transaction per side, then every transaction of the period (date, +/- sign, amount, desc).
- transaction.SummarizeUseCase (internal/usecase/transaction/summarize.go) pre-filters on summaryKeywords, then MessageParser.ParseSummary (Gemini) resolves the date range. It runs in the dispatcher after register/split and before transaction.QueryUseCase; handled=false falls through.
- Max range is 1 month (inclusive, so 1 Aug–31 Aug ok, 1 Aug–1 Sep too long) -> message.SummaryRangeTooLong. Transactions with amount 0 (still awaiting an amount) are left out. A side with no transactions renders as *none* and its insights are dropped; no transactions at all reuses message.QueryNoResults.
- Fetches everything via ListByUserBetween with limit -1 (SQLite: no limit), no paging.

## Frankie persona (done)
The bot speaks as *Frankie*, a friendly creature stitched together in a lab who tracks the user's money and calls them "bos".
- Error replies: replyForError() (dispatcher.go) maps the error to a message.PoolKey and asks persona.Picker (internal/usecase/persona) for a variant from message.ErrorPools. The picker never repeats the last variant a user saw from the same pool (in-memory, resets on restart) and fills [[greeting]] by Asia/Jakarta time of day. Language comes from persona.DetectLang (Indonesian keyword check, defaults to English) — no model call. Instead of a visible error code, the code's emoji (message.ErrorEmoji: 400 🧪, 404 🕯️, 409 🧷, 503 🌩️, 500 🧠) is appended on the same line, and the dispatcher logs "error reply sent" with the sender and code. Error variants must not contain emoji themselves (enforced by a test).
- Pooled error replies have no fixed first line, so they're not in BotReplyPrefixes; IsFromMe is what guards them. Every variant for not-registered must keep the exact "register <name> <email>" instruction (enforced by a test).
- Transaction quips: Parse's Gemini schema has an optional "quip" field (same request, no extra call). transaction.RecordUseCase shows a quip on every new income (message.QuipIncomeChancePct, 100%) and on message.QuipExpenseChancePct (35%) of new expenses, as a separate message sent right after the confirmation (so users don't mistake it for part of the record). The quip message is NOT linked to the transaction: a transaction has one wa_message_id and it must stay the confirmation's, so replying to the confirmation keeps working. Every quip starts with message.QuipPrefix ("💬 "), which is also in BotReplyPrefixes; a reply whose quoted text starts with it (and whose stanza ID isn't linked to a transaction or page) gets a PoolReplyToQuip error reply (🧪) pointing the user to the confirmation, and nothing is recorded. All Frankie replies are English (message.ReplyLang = LangEN), to match the English templates: error replies use the English pools, and quips are English via the prompt rule + English-only pools; a model quip that persona.IsEnglish rejects (Indonesian words other than amounts like "ribu") is dropped for a pool quip. Set ReplyLang to "" to make error replies follow the user's language again (the Indonesian error pools are kept for that). The model's quip is untrusted: persona.SanitizeQuip strips newlines and WhatsApp formatting characters and caps the length. If it's empty, a fallback comes from message.QuipByCategory / QuipExpenseDefault / QuipIncome. A reply that fills in the amount of an *AMOUNT NEEDED* transaction counts as new and follows the same rule (pooled quip only, since ParseAmend has no quip field); other amend re-renders, *AMOUNT NEEDED* itself and query listings get no quip. The shared rule is newTransactionQuip in internal/usecase/transaction/record.go.
- Reply language: persona.Picker.Lang(userJID, text) detects it and remembers it per user (in memory), so a message with no words, like a bare amount, reuses the user's last language.
- persona.Picker is created once in wire.go and shared by the dispatcher and transaction.RecordUseCase; tests use persona.NewWithSource for a fixed seed and clock.

## Per-chat queue, typing pause, daily greeting (done)
- whatsmeow calls event handlers on one serial loop, so the Handler's handleEvent only filters/extracts the message and hands the rest (Handler.process) to a chatQueue (internal/external/whatsapp/queue.go): one worker goroutine per chat, jobs in arrival order, chats in parallel; a worker exits after chatIdle (5 min) without messages, and a panicking job is logged instead of crashing the bot. SQLite writes from parallel chats rely on the DSN's _busy_timeout=5000.
- response.Reply.Typing: the handler shows "typing..." for typingDelay(text) (700 ms + 20 ms/char, max 2 s) before sending that reply. Set on Frankie's chatty messages (the quip); data messages (confirmations, listings) keep the short sendInterval. The pause only delays that chat.
- Daily greeting: on a user's first transaction of the day (Asia/Jakarta), transaction.RecordUseCase sends a greeting message first (message.DailyGreetingPools by part of day, with [[name]] = the registered name). "First today" = TransactionRepository.LastCreatedAt (newest by id) is not on the same Jakarta day (persona.SameDay), checked before saving — so it survives restarts, with no schema change. Timestamps are compared in Go, not SQL, because stored created_at strings carry whatever UTC offset the process had.
